# Fun experiment but not recommended. 
Our LLM models are so powerful that they "will" figure it out. 
- on very, very tough problems this tool will drastically cut down token use and time for resolution. 
- on the **absolute majority** of code-understand challenges, this tool is makign the LLMs less efficient. 

For this reason I am abandoning this hackathon test tool. It was interesting to see if codebase scaffholding and understanding makes as difference and how. The answer is that it "does" but it's in general is better to let the models figure it out for themselves in say up to 1 million lines of code big repos. (just help them with structured approach). 

At this point honestly, I don't remember if it was branch 0.0.3 or main that was the best version of this. I think one of them was good and the other one was 💩. Either way, I have it available now in case some random discovers it and have been thinking along the same ways. 


# repo-understand

Analyze any git repository and generate documentation that helps AI agents
understand and navigate the codebase.

## Quick start

This script is a **standalone tool** that you point at a target repository.
It does not need to live inside the repo being analyzed.


#### Clone and run
```bash
git clone git@github.com:KjellKod/repo-understand.git
```
#### run it 
```
./repo-understand/repo-understand.sh /path/to/target/repo
```

Requirements: `jq` (`brew install jq` on macOS, `apt-get install jq` on Linux).
Works on macOS bash 3.2+. No other dependencies.

## What it generates

The script produces 5 markdown files and a manifest. By default, output is
written into the **target repo** (not where the script lives):

```
<target-repo>/
├── docs/
│   └── architecture/
│       ├── overview.md           # Architecture overview
│       ├── tech-stack.md         # Languages, frameworks, databases
│       └── directory-map.md      # Annotated directory tree
├── agents-content.md             # Boundaries and rules for AI agents
├── doc-structure.md              # Documentation navigation map
└── repo-understand.manifest.json # Staleness metadata (git SHA + timestamp)
```

| File | Purpose |
|------|---------|
| `docs/architecture/overview.md` | High-level architecture, monorepo structure, key patterns |
| `docs/architecture/tech-stack.md` | Languages, frameworks, databases, build tools |
| `docs/architecture/directory-map.md` | Annotated directory tree with file counts and descriptions |
| `agents-content.md` | Architecture boundaries, rules, and testing guidance for agents |
| `doc-structure.md` | Documentation navigation map |
| `repo-understand.manifest.json` | Generation metadata (git SHA, timestamp, file count, scan time) |

All generated files include a `<!-- GENERATED by repo-understand -->` header
and YAML frontmatter. They are safe to overwrite on re-run.

## Options

```bash
# Analyze repo, write output into the target repo itself (default)
/path/to/repo-understand.sh /path/to/target/repo

# Write output to a different directory instead
/path/to/repo-understand.sh /path/to/target/repo --output /tmp/docs

# Preview what would be generated without writing any files
/path/to/repo-understand.sh /path/to/target/repo --dry-run
```

## How it works

**Phase 1 -- Analyzers** produce JSON fragments in a temp directory
(`/tmp/repo-understand.XXXXXX/`, deleted automatically when the script
finishes):

| Analyzer | What it extracts |
|----------|-----------------|
| `structure.sh` | Directory tree, file counts by extension, monorepo detection |
| `tech-stack.sh` | Languages, frameworks, databases, build tools (from package.json, go.mod, etc.) |
| `dependencies.sh` | Inter-package dependency graph, external dependency count |
| `patterns.sh` | Architectural patterns (routes, models, controllers, middleware, tests) |
| `git-insights.sh` | Active contributors, commit frequency, hotspot files, stale directories |

**Phase 2 -- Generators** consume the JSON and produce the markdown files
listed above, written into the target repo (or `--output` dir).

**Phase 3 -- Manifest** writes `repo-understand.manifest.json` with the git SHA
and timestamp so agents can detect staleness later.

## Staleness detection

The manifest records the git SHA at scan time. Agents can check how stale the
docs are by running:

```bash
git rev-list --count <sha-from-manifest>..HEAD
```

The generated `agents-content.md` includes a staleness warning snippet that
tells agents to suggest re-running if more than 50 commits behind. Staleness
is commit-count primary, with time as context:

- 0 commits behind + 5 years old = fine (nothing changed)
- 100 commits behind + 1 day old = stale (re-run recommended)

## Using the output with AI agents

Once generated, the docs live in the target repo. You need to tell agents
to read them. There are several approaches:

### 1. Reference in AGENTS.md or CLAUDE.md

Add a section to the target repo's agent instructions file:

```markdown
## Repository Context (generated by repo-understand)

Before starting work, read these generated docs:
- `docs/architecture/overview.md` -- system architecture
- `docs/architecture/tech-stack.md` -- technology stack
- `docs/architecture/directory-map.md` -- where things are

Architecture boundaries and rules are in `agents-content.md`.

> Staleness: check `repo-understand.manifest.json` for the git SHA.
> Run `git rev-list --count <sha>..HEAD` -- if 50+ commits behind,
> re-run repo-understand.sh before starting.
```

### 2. Merge agents-content.md into your AGENTS.md

The `agents-content.md` file is designed to be copied (or included) into
the target repo's AGENTS.md. It contains architecture boundaries, boundary
rules, testing expectations, and entry points -- all specific to that repo.

### 3. Use doc-structure.md as a navigation index

The `doc-structure.md` output is a documentation map. Include it in the
target repo's DOCUMENTATION_STRUCTURE.md or equivalent so agents know
where to find detailed docs when they need them.

### Key principle

These docs serve as "Layer 1" context -- they answer "what is this repo?"
at near-zero token cost compared to agents scanning the filesystem themselves.
They do not replace deep code reading for implementation work, but they
eliminate the cold-start overhead of understanding repo layout, tech stack,
and conventions.

## Re-running

The script is idempotent. Re-running overwrites all generated files with
fresh analysis. Run it after significant structural changes (new packages,
major refactors, tech stack changes).

```bash
/path/to/repo-understand.sh /path/to/target/repo
```

## Benchmark harness — prove that scaffolding works

> **Full walkthrough: [BENCHMARK_WALKTHROUGH.md](BENCHMARK_WALKTHROUGH.md)**
>
> Step-by-step guide covering generic tasks, writing your own domain-specific
> tasks, interpreting results, and where all artifacts end up.

The `benchmark/` directory measures whether the generated docs actually reduce
time, tokens, and errors when agents work on a repo. Agents run in **full
agent mode** with file access — not single-turn prompts.

```bash
BENCHMARK_DIR=/path/to/repo-understand/benchmark

# Run WITHOUT scaffolding (agent explores from scratch)
$BENCHMARK_DIR/benchmark.sh /path/to/target/repo $BENCHMARK_DIR/tasks/explain-architecture.md --without-scaffolding

# Run WITH scaffolding (generated docs are in the repo for the agent to find)
$BENCHMARK_DIR/benchmark.sh /path/to/target/repo $BENCHMARK_DIR/tasks/explain-architecture.md --with-scaffolding

# Judge scoring runs automatically after each benchmark.
# To re-judge a previous result manually:
$BENCHMARK_DIR/benchmark.sh /path/to/target/repo $BENCHMARK_DIR/tasks/explain-architecture.md --judge benchmark/results/<result>.json

# Generate comparison report
$BENCHMARK_DIR/report.sh
```

### Benchmark options

| Flag | Default | Description |
|------|---------|-------------|
| `--without-scaffolding` | | Agent explores from scratch (baseline) |
| `--with-scaffolding` | | Generate docs first, agent can discover them |
| `--model <model>` | `sonnet` | Model to use (e.g. `opus`, `haiku`, `sonnet`) |
| `--max-budget <usd>` | `0.50` | Max spend per run in USD |
| `--no-judge` | | Skip automatic judge scoring after benchmark |
| `--judge <result-file>` | | Re-judge a previous result for accuracy |
| `--answer-key <file>` | | Answer key for judge scoring (improves accuracy) |

See the [walkthrough](BENCHMARK_WALKTHROUGH.md) for the full guide including
how to write domain-specific tasks, use answer keys, and interpret results.
